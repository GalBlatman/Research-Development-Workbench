GOAL

Build a reproducible benchmark and ablation harness that can later test whether
the Workbench:

- recognizes the scientific feature actually present;
- notices when an important feature is removed or degraded;
- does not invent information that was hidden;
- changes only judgments that should change;
- recognizes repair/restoration;
- preserves uncertainty when the remaining packet cannot answer a question;
- outperforms a simple baseline evaluator enough to justify its complexity;
- reports token/cost/run metadata.

This step builds the HARNESS.

It does NOT build the 50-paper benchmark corpus.
It does NOT calibrate the rubric.
It does NOT tune against published-paper outcomes.

CRITICAL BLINDNESS ARCHITECTURE

The blind evaluator must be architecturally unable to access:

- gold answers;
- hidden feature content;
- transformation labels that reveal what was removed;
- expected outcomes;
- publication/journal metadata unless the variant explicitly permits it;
- sibling variants of the same paper where that would reveal hidden content.

Do not merely rely on prompt instructions such as:
"Do not look at the gold answer."

Enforce access separation in code/data boundaries.

The component constructing benchmark variants may access gold data.

The evaluator-facing ContextPacket may access only the material admitted for
that particular variant.

Add tests proving evaluator code cannot retrieve gold/hidden content through
normal repository/service interfaces.

- DEVELOPMENT
- VALIDATION

same split.

- baseline/evaluator caches that leak outputs between splits.

Support a frozen split manifest with content hashes.

VARIANT TYPES

Support at least these transformation classes.

1. INTACT_BLIND
   Full permitted benchmark packet with identifying/publication metadata removed
   where appropriate.

2. HIDE_FEATURE
   Remove one target feature while leaving unrelated content intact.

3. HIDE_MULTIPLE
   Remove a specified pair or selected higher-order combination.

4. CUMULATIVE_REVEAL
   Begin with a reduced packet and reveal defined information in stages.

5. CONTROLLED_DEGRADATION
   Replace a valid component with a weaker but plausible alternative.

6. CONTROLLED_RESTORATION
   Restore a previously removed/degraded component.

7. METADATA_BLINDING
   Strip title/authors/journal/DOI/publication status/citations/awards where
   appropriate.

Do not attempt every possible combinatorial subset.

The harness must support selected combinations determined by benchmark design.

CONTROLLED DEGRADATIONS

The framework must be able to represent transformations such as:

- valid construct measure -> adjacent proxy;
- longitudinal ordering -> cross-sectional evidence;
- serious rival -> straw rival;
- bounded claim -> overbroad claim;
- explanatory mechanism -> restated association;
- explicit premise evidence -> unsupported premise;
- completed evidence -> merely proposed evidence;
- source-grounded novelty claim -> unsupported novelty assertion.

The harness must record exactly what transformation was made without exposing
that transformation to the blind evaluator.

Do not generate these actual paper mutations yet except minimal synthetic test
fixtures required to verify the harness.

CORRECT BEHAVIOR IS NOT ALWAYS RECONSTRUCTION

Encode this explicitly.

If a feature is hidden, success may be:

- "cannot determine from supplied material";
- PENDING;
- NOT_INSPECTED;
- UNRESOLVED;
- withholding a score/judgment;
- narrowing the claim.

The harness must NOT define success as reconstructing the hidden gold answer.

An evaluator that hallucinates the correct hidden mechanism from memory or model
training is not necessarily behaving correctly.

TARGETED EXECUTION

A benchmark case must be able to execute only the relevant Workbench component.

Examples:
- mechanism ablation -> argument/mechanism assessment and necessary checker;
- measure degradation -> Study assessment and necessary checker;
- literature mutation -> Literature/contribution assessment;
- rival mutation -> Alternatives assessment.

Do not require a full project evaluation for every benchmark case.

Also support FULL_WORKBENCH runs for integration testing.

Record which components actually ran.

BASELINE EVALUATOR

Implement a deliberately simple comparator:

Same:
- model/provider configuration;
- benchmark packet;
- applicable rubric;
- output schema where feasible.

But:
- one well-written evaluation prompt;
- no Workbench multi-stage workflow;
- no elaborate internal revision/checking pipeline beyond what is necessary for
  valid structured output.

The purpose is to answer:

"Does the Workbench workflow materially outperform a much simpler evaluator?"

Do not sabotage the baseline.
Do not make its prompt intentionally weak.

Keep baseline results separate from Workbench results.

LEAKAGE / RECOGNITION DIAGNOSTICS

Support diagnostics for possible memorization or identity leakage.

Record, where tested:
- whether the evaluator claims to recognize the paper;
- whether hidden identifying metadata appears in output;
- whether hidden content is reproduced with suspicious specificity;
- whether results change under neutral paraphrase/anonymization.

Do not assume recognition proves contamination.
Flag it for interpretation.

The harness should permit:
- original neutral decomposition;
- substantively equivalent anonymized/paraphrased packet.

Do not implement automated plagiarism detection.

METRICS

Implement feature-level and run-level metrics.

At minimum support:

A. DETECTION SENSITIVITY
Did the relevant judgment change when the target feature was removed/degraded?

B. INVARIANCE / ISOLATION
Did unrelated judgments remain appropriately stable?

C. WITHHOLDING ACCURACY
When evidence became insufficient, did the evaluator withhold or mark uncertainty
rather than invent?

D. RESTORATION RECOGNITION
When valid content was restored, did the relevant judgment recover?

E. DIRECTIONAL SENSITIVITY
For degradations, did affected assessments move in the scientifically expected
direction when an expected direction is defined?

F. SOURCE ATTRIBUTION ACCURACY
Did claims remain tied to permitted evidence?

G. STATE ACCURACY
Did PENDING / NOT_INSPECTED / NOT_APPLICABLE / CONTRADICTED / etc. remain
correct?

H. INVARIANT VIOLATIONS
What unrelated decisions changed unexpectedly?

I. ACTION RELEVANCE
Did recommended next actions target the manipulated weakness?

J. COST / EFFICIENCY
Record:
- calls;
- input tokens;
- output tokens;
- provider-reported usage;
- estimated/known cost inputs;
- wall-clock duration where measurable.

Do not convert these into one magic composite score.

REPORT both:
- case-level metrics;
- paper-level aggregated metrics.

Repeated variants from one paper are nested observations, not independent
papers.

EXPECTATION DESIGN

Benchmark expectations must be explicit and typed.

Examples:

Hide mechanism:
- mechanism judgment should not remain confidently supported;
- model need not reconstruct gold mechanism;
- unrelated source/provenance judgments should remain stable.

Replace valid measure with adjacent proxy:
- construct-measure fit should worsen or become unresolved;
- literature novelty should not change merely because the measure changed.

Replace serious rival with straw rival:
- strength-of-alternatives assessment should weaken;
- unrelated empirical facts should remain stable.

Restore valid measure:
- affected Study judgment should recover if nothing else changed.

The harness must allow expectations with:
- expected change;
- expected no-change;
- acceptable set of states;
- forbidden state;
- no directional expectation.

Do not encode journal acceptance as the gold outcome.

GOLD STORE / EVALUATOR SEPARATION

Gold decompositions and variant-generation metadata must use a storage/service
boundary distinct from evaluator-facing content.

Normal Workbench/model code must not have repository/service permissions to read
gold answers.

Tests must demonstrate:
- blind evaluator cannot fetch gold by benchmark ID;
- blind evaluator cannot enumerate sibling hidden variants;
- run artifacts cannot expose gold expectation metadata to the provider request;
- exports intended for evaluator inspection exclude gold fields.

Synthetic harness-admin tools may access gold.
